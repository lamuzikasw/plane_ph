# Обновление Plane через GitHub

Управление: [Actions → Deploy Plane](https://github.com/lamuzikasw/plane_ph/actions/workflows/deploy-plane.yml).
В админке Plane ничего настраивать не нужно.

1. Изменения отправляются на GitHub. **Plane CI** автоматически проверяет PR и коммиты в `main`.
2. Откройте **Deploy Plane → Run workflow**, выберите `main` и нажмите зелёную кнопку.
3. Дождитесь зелёного результата **Update production**. Внутри запуска видны проверки, сборка и журнал обновления.
4. Обновите страницу [Plane](https://plane.myneogroup.space).

Можно попросить разработчика или Codex запустить тот же workflow. Ручной SSH для обычного выпуска не нужен.
Право запуска определяется доступом к репозиторию GitHub, а не ролью в Plane.

## Что входит в MVP

Автоматизация выпускает **API, фоновые задачи и основной веб-интерфейс**.
Admin, Space, Live, proxy и инфраструктурные сервисы остаются на своих текущих версиях.
Изменения этих компонентов требуют отдельного выпуска или расширения этого workflow.

CI запускает unit-тесты API, проверяет миграции на отдельной БД, тесты веб-приложения,
производственную сборку, TypeScript и lint веб-приложения и его зависимостей.
Это не полное браузерное тестирование всех сценариев.

Ручной запуск повторяет проверки для конкретного коммита, собирает Docker-образы с его SHA
и передаёт их серверу. Production принимает только `main`; одновременные деплои сериализованы.
Перед миграциями создаётся PostgreSQL dump и сохраняются предыдущие образы в конфигурации.
После обновления проверяются API, контрольная сумма веб-страницы и ответ Celery worker.
При перезапуске возможен короткий перерыв в работе сайта.

## Если выпуск красный

Откройте красный шаг и прочитайте конец журнала. Ошибка тестов/сборки не меняет сервер.
Ошибка миграции останавливает выпуск до переключения приложения; сама миграция могла
успеть применить часть изменений. Ошибка после переключения запускает возврат предыдущих
образов и проверку их работоспособности. После исправления запускайте **новый** выпуск из `main`.

**База автоматически назад не откатывается:** это могло бы удалить новые пользовательские данные.
Миграции должны быть совместимы с предыдущей версией приложения. Удаление/переименование полей
и другие несовместимые изменения требуют отдельного плана с разработчиком.
При `ROLLBACK HEALTH CHECK FAILED` нужен оператор с SSH-доступом.

## Для администратора

- Сервер: `187.77.70.240`, рабочая установка `/opt/plane/plane-app`.
- GitHub environment `production`: secret `PLANE_DEPLOY_KEY`, variables `PLANE_SSH_HOST`, `PLANE_KNOWN_HOSTS`.
- Ключ выделенный, Ed25519. Личный ключ разработчика в GitHub не используется.
- CI использует существующего пользователя `deploy`, но отдельный ключ принимает только команду
  `deploy COMMIT_SHA INDEX_SHA256`. Для этого ключа интерактивная оболочка, PTY и SSH forwarding закрыты.
  Доверенные скрипты принадлежат root. SSH-политика сервера и обычный ключ администратора не меняются.
- Скрипты устанавливаются через `sudo bash deploy/install.sh /path/to/ci-key.pub`.
  Изменение скриптов в GitHub само по себе не заменяет доверенный скрипт сервера: его обновляет оператор.
- Резервные копии: `/opt/plane/backups/<timestamp>-<sha>/database.dump` и `docker-compose.override.yaml`.
- Последний успешный выпуск: `/opt/plane/releases/current.json`.
- Образы: `local/plane-backend:ci-<sha>` и `local/plane-frontend:ci-<sha>`.
- Перед загрузкой образов текущие контейнеры сохраняются под тегами `local/plane-rollback:<release>-<service>`.
  Это сохраняет возможность возврата даже при повторном выпуске того же коммита.
- Артефакты GitHub хранятся 7 дней. Резервные копии и старые образы на сервере автоматически не удаляются;
  периодически очищайте только старые выпуски Plane, сохраняя текущий и предыдущий. Не запускайте общий Docker prune.
  При свободном месте меньше 5 GiB выпуск остановится до изменения приложения.
- Для отключения CI-доступа удалите только строку ключа `plane-ph-github-actions`
  из `/home/deploy/.ssh/authorized_keys` и GitHub secret; остальные ключи сохраните.

Восстановление приложения вручную: сохраните текущий override, верните override из нужной резервной копии
и выполните `sudo ./compose-safe.sh up -d --no-deps api worker beat-worker web` из каталога установки.
Перед этим проверьте совместимость миграций. Восстановление БД — отдельная операция с остановкой записи
и оценкой потери данных; workflow её не выполняет.
