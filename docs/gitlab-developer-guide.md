# Инструкция для разработчиков по работе с GitLab в Plane

Эта инструкция объясняет, как связать работу в GitLab с задачей Plane.
В разделе **Разработка / Development** можно увидеть ветки, merge requests (MR),
коммиты и результаты CI, а затем перейти к нужному объекту в GitLab.

**Основной сценарий: укажите ключ задачи в имени ветки, отправьте ветку в GitLab
и создайте MR из неё.** Plane привяжет ветку и MR автоматически. Коммиты MR,
pipelines и jobs появятся под MR после синхронизации.

Для работы команды администратор должен подключить GitLab и нужные репозитории
в вашем workspace. Личный аккаунт каждый разработчик подключает самостоятельно.

## Подключить личный GitLab аккаунт

1. Откройте задачу Plane и найдите раздел **Разработка / Development**.
2. Нажмите **Подключить мой GitLab аккаунт / Connect my GitLab account**.
3. Войдите в свой рабочий аккаунт GitLab и разрешите доступ `read_api`.
4. После возвращения в Plane проверьте, что рядом с подключением указан ваш
   GitLab username.

Для просмотра нужны доступ к задаче Plane и личный доступ к коду репозитория
GitLab. Доступ к CI сам по себе недостаточен. Если некоторые категории закрыты
для вашего аккаунта в GitLab, соответствующие данные будут скрыты в Plane.

Если раздел сообщает, что GitLab не подключён, обратитесь к администратору
workspace. Если нет кнопки подключения личного аккаунта, попросите его проверить
настройку OAuth. Общие токены и OAuth приложение настраивает администратор;
разработчику достаточно подключить свой аккаунт через кнопку.

## Ежедневная работа с задачей

В примерах ниже `PLGIT-123` — ключ задачи Plane. Замените его реальным ключом
из карточки задачи. Задача должна существовать в том же workspace,
к которому подключён репозиторий.

1. Откройте задачу и скопируйте её ключ.
2. Начните работу от актуальной основной ветки репозитория по обычному процессу
   команды и создайте ветку с ключом задачи:

   ```sh
   git switch -c feature/PLGIT-123-add-payment
   ```

3. Внесите изменения, создайте коммит и отправьте ветку в GitLab:

   ```sh
   git push -u origin feature/PLGIT-123-add-payment
   ```

   После синхронизации ветка появится в блоке **Ветки / Branches** задачи.
   Ветку, которая существует только на вашем компьютере, Plane не видит.

4. Создайте в GitLab MR из этой ветки. Если исходная ветка находится в подключённом
   репозитории, MR автоматически привяжется к задаче по её имени. Заголовок MR
   может быть обычным, например `Добавить оплату картой`.
5. Продолжайте отправлять изменения в ту же ветку. Коммиты, входящие в связанный
   MR, и их доступные pipelines и jobs подтянутся в задачу. Добавлять маркер
   в каждый такой коммит не требуется.
6. Проверяйте CI в разделе **Разработка**. Для логов, artifacts и повторного
   запуска job откройте его ссылку в GitLab. Эти действия зависят от ваших прав
   в GitLab; подключение к Plane их не расширяет.
7. Выполните review и merge в GitLab. Обновите статус задачи Plane по процессу
   команды: слияние MR автоматически не переводит задачу в Done.

Подходят, например, имена `feature/PLGIT-123-add-payment`,
`fix/PLGIT-123-validation` и `PLGIT-123-refactor`. Используйте полный ключ
и дефисы, как в Plane; в номере задачи не должно быть ведущих нулей.

До появления MR блок ветки показывает её название, состояние и текущий head SHA.
Коммиты и CI доступны через связанный MR или отдельную привязку коммита,
pipeline либо job. Чтобы показать конкретный коммит до создания MR,
используйте маркер в его сообщении или добавьте URL вручную.

## Привязать MR или коммит через маркер

Если имя ветки не содержит ключ задачи, укажите `plane:PLGIT-123`
в **заголовке или описании MR**. Например:

```text
Добавить оплату картой

Задача: plane:PLGIT-123
```

Для самостоятельной привязки коммита используйте маркер в его сообщении:

```text
fix: исправить проверку суммы plane:PLGIT-123
```

Пишите `plane:` строчными буквами и слитно с ключом задачи.

| Где указан ключ                                  | Что привязывается                            |
| ------------------------------------------------ | -------------------------------------------- |
| `feature/PLGIT-123-add-payment` в имени ветки    | Ветка и MR из неё в подключённом репозитории |
| `plane:PLGIT-123` в заголовке или описании MR    | MR, его коммиты и доступный CI               |
| `plane:PLGIT-123` в сообщении коммита            | Коммит и его доступный CI                    |
| `PLGIT-123` без `plane:` в тексте MR или коммита | Автопривязка по этому тексту не создаётся    |

Комментарий к MR не служит местом для маркера: используйте заголовок
или описание самого MR. Маркер связывает с существующей задачей;
новую задачу Plane он не создаёт.

Для MR из fork используйте явный маркер `plane:PLGIT-123`. Привязка по имени
исходной ветки работает, когда её GitLab project совпадает с подключённым
репозиторием, в котором синхронизируется MR. CI из другого source project
автоматически в это дерево не переносится; при необходимости попросите
подключить исходный репозиторий и добавьте URL его pipeline отдельно.

## Связать работу с несколькими задачами

В имени ветки можно указать несколько ключей:

```text
feature/PLGIT-123-PLGIT-124-shared-validation
```

Такая ветка и MR из неё появятся в обеих задачах. Другой вариант — перечислить
маркеры в описании MR или сообщении коммита:

```text
Задачи: plane:PLGIT-123 plane:PLGIT-124
```

Указывайте только задачи, к которым относится работа: связанный MR показывает
в задаче все свои доступные коммиты и CI.

## Добавить связь вручную

Ручная связь полезна для уже существующего MR, коммита или отдельного запуска CI.

1. Скопируйте в GitLab URL нужной ветки, MR, коммита, pipeline или job.
2. В разделе **Разработка** вставьте его в поле
   **URL ветки, MR, коммита, pipeline или job в GitLab**.
3. Нажмите **Добавить связь / Add link**.

Ссылка должна вести на настроенный GitLab и подключённый репозиторий.
Для ветки копируйте URL самой ветки, без пути к файлу или каталогу внутри неё.
Для коммита используйте ссылку с полным SHA.

Добавление MR подтягивает его дерево; добавление коммита — его pipelines и jobs;
добавление pipeline — его jobs. **Добавление URL job сразу закрепляет именно
этот запуск** в задаче. Повторное добавление того же объекта не создаёт копию.

Для изменения связей нужно право редактирования задачи Plane и личный доступ
к соответствующему объекту GitLab. В архивных задачах и проектах связи
редактировать нельзя.

## Читать раздел Разработка

Ветки находятся в отдельном блоке. Для MR указаны его номер, заголовок,
состояние и направление веток. Под MR можно раскрыть коммиты, затем pipelines
и их jobs. Pipeline может отображаться непосредственно под MR, если он относится
к результату слияния. Нажатие на название объекта открывает GitLab.

У коммита можно раскрыть **Полное сообщение коммита / Full commit message**.
Pipeline — запуск CI, а jobs — отдельные проверки или шаги этого запуска.
У pipeline видны статус и сводка jobs, у job — стадия и длительность,
если GitLab предоставил эти данные. Пометка **Допускается ошибка / Allowed to fail**
означает, что для job задано `allow_failure`.

Под объектами указана причина связи:

| Пометка                    | Значение                                               |
| -------------------------- | ------------------------------------------------------ |
| Имя ветки / Branch name    | Связь создана по ключу задачи в исходной ветке         |
| Маркер / Marker            | В GitLab найден `plane:PROJECT-123`                    |
| Вручную / Manual           | Объект добавлен по URL                                 |
| Через родителя / Inherited | Объект показан через связанный MR, коммит или pipeline |
| Закреплён / Pinned         | В задаче закреплён конкретный запуск job               |

У объекта может быть несколько причин связи. Если нужный объект не виден,
раскройте **История / History**, **Ещё jobs / More jobs** или сам pipeline.
Повторённые jobs и удалённые ветки сохраняются в истории.

## Закрепить результат CI

Когда для задачи важен конкретный результат проверки, раскройте pipeline,
найдите нужный job и нажмите **Закрепить этот job / Pin this job**.
Он появится в блоке **Закреплённые jobs / Pinned jobs** со ссылками на свой
pipeline и коммит.

Закрепление относится к точному запуску job. Если повторить job в GitLab,
старый запуск останется закреплённым; новый можно закрепить отдельно.
Закреплённый job может одновременно отображаться в своём pipeline.

Кнопка **Открепить / Unpin** снимает закрепление. Если job доступен через
связанный MR или pipeline, он продолжит отображаться в дереве.

## Убрать или восстановить связь

Нажмите **Убрать связь / Unlink** у нужного объекта. Это скрывает выбранную связь
в этой задаче; повторная синхронизация автоматически её не восстанавливает.
Объект GitLab остаётся на месте, связи с другими задачами сохраняются.
Убирайте связь с веткой и MR отдельно: они привязаны к задаче независимо.

Чтобы восстановить связь, снова добавьте URL этого объекта через **Добавить связь**.
Объект должен оставаться доступным в GitLab. Если ветка была удалена в GitLab,
добавить её заново можно после восстановления самой ветки.

## Когда появятся изменения

Plane опрашивает GitLab раз в **5 минут**. Видимый раздел задачи
перечитывает данные Plane примерно каждые **15 секунд**;
он также обновляется при возвращении на вкладку.

Иконка обновления рядом с заголовком раздела имеет подпись
**Обновить связи с GitLab / Refresh development links**. Она перечитывает
доступные данные Plane и проверяет ваши права. Кнопка не запускает немедленную
серверную синхронизацию с GitLab.

После push или создания MR дождитесь очередной синхронизации и её завершения.
При доступном webhook обновления поступают через события GitLab; удалённая
доставка webhook в локальном пилоте ещё не подтверждена. Сообщение
**Последняя синхронизация** относится ко всему подключению, а не к каждому
объекту отдельно.

## Если данные не появились

| Ситуация                         | Что проверить                                                                                                                                      |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ветка не появилась               | Ветка отправлена в GitLab; имя содержит правильный ключ существующей задачи; репозиторий подключён к нужному workspace; синхронизация завершилась  |
| MR не привязался                 | Исходная ветка содержит ключ и находится в том же подключённом репозитории, либо в заголовке/описании MR есть `plane:PROJECT-123`                  |
| Новый коммит не виден            | Он входит в связанный MR либо содержит собственный маркер; изменения отправлены в GitLab; очередь синхронизации успела их обработать               |
| Нет pipelines или jobs           | CI существует в GitLab, доступен вашему аккаунту и принадлежит подключённому репозиторию; pipeline и история раскрыты                              |
| Раздел просит подключить аккаунт | Подключите личный GitLab; при необходимости нажмите **Переподключить GitLab** и проверьте доступ к коду репозитория                                |
| Ссылка не добавляется            | Использован URL поддерживаемого объекта с настроенного сервера и подключённого репозитория; есть права редактировать задачу и читать объект GitLab |
| Связь раньше была убрана         | Добавьте URL повторно: синхронизация не отменяет ручное удаление связи                                                                             |
| Показана ошибка синхронизации    | Проверьте время последней синхронизации и обратитесь к администратору, приложив ключ задачи, URL объекта и текст ошибки                            |

При недоступности GitLab данные могут обновляться с задержкой. Если личную
проверку прав выполнить не удалось, Plane скрывает данные до успешной проверки.

Настройка сервера, репозиториев, OAuth и webhook описана отдельно в
[руководстве для администратора](gitlab-development.md).
