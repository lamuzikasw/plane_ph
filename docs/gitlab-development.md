# GitLab Development: локальный пилот

Для ежедневной работы с задачами используйте
[инструкцию для разработчиков](gitlab-developer-guide.md).

Интеграция добавляет в карточку задачи раздел **Development / Разработка**:
ветки и дерево MR → коммиты → pipelines → jobs. Прямые ссылки добавляются по URL. Маркер
`plane:PROJECT-123` в сообщении коммита, заголовке или описании MR создаёт
автоматическую связь. Один объект может принадлежать нескольким задачам.
Ключ `PROJECT-123` в имени ветки, например `feature/PROJECT-123-payment`,
автоматически показывает ветку в отдельном блоке **Branches / Ветки** ещё до MR.
MR из этой ветки тоже связывается с задачей по имени исходной ветки, если его
source project совпадает с подключённым репозиторием. Для текста MR и коммитов
продолжает использоваться явный маркер `plane:`.

## Подключение

1. Применить миграции API и перезапустить API, Celery worker и beat.
2. В GitLab создать отдельный технический токен с **Reporter** и только
   **read_api** для выбранных репозиториев. Интеграция проверяет scope и роль.
3. Создать confidential OAuth application со scope **read_api**. Callback:
   `http://127.0.0.1:8000/api/integrations/gitlab/callback/` для локального API.
   Для другого окружения использовать его внешний адрес API.
4. Администратор workspace открывает Settings → Integrations → GitLab:
   адрес HTTPS сервера, числовые ID репозиториев, технический токен,
   OAuth Application ID / Secret. Несколько серверов подключаются отдельно.
5. Каждый пользователь нажимает **Connect my GitLab account** в задаче.
   Его OAuth credentials хранятся зашифрованными на сервере; refresh token
   обновляется с блокировкой строки и заменой предыдущего значения.
   Одноразовое OAuth состояние хранится в отдельной таблице, привязано к
   пользователю и сессии, истекает через 10 минут и атомарно погашается.
   Параллельные запросы других вкладок не перезаписывают это состояние.
6. В настройках GitLab project добавить webhook с URL и secret из Plane.
   События: Push, Tag Push, Merge Request, Pipeline, Job. Оставить SSL verification.

GitLab должен иметь сетевой доступ к API Plane. Удалённый GitLab не может
отправлять события на `127.0.0.1` компьютера разработчика: для прямой доставки
нужен согласованный доступный HTTPS адрес. Локальная работа без такого адреса
использует API reconciliation каждые 5 минут. HTTP endpoint также можно проверять
локальными запросами с webhook secret; это не подтверждает удалённую доставку.

## Поведение и права

- Технический токен используется только для GET запросов к repository API.
  Интеграция не запускает, не отменяет и не повторяет CI; не меняет задачи.
- Просмотр требует доступа к задаче Plane и личного доступа к коду GitLab.
  Успешный GET project или доступ к CI недостаточен: Guest в GitLab 18.9
  может видеть CI без доступа к коду. Проверка выполняется при каждом чтении;
  при недоступности проверки данные скрываются.
- Дополнительно проверяется доступ к спискам веток, MR, pipelines и jobs. После
  обязательной проверки доступа к коду эти четыре запроса выполняются параллельно.
  Закрытые категории скрываются. Удаление доступа вступает в силу при следующем запросе.
- Изменение связей требует права редактирования задачи. Ручной URL должен
  принадлежать настроенному серверу и разрешённому репозиторию.
- Ветки требуют личного доступа к repository/branches в дополнение к коду.
  Блок веток показывает название, ссылку GitLab, head SHA и состояние.
  Привязка по имени помечена как **Branch name / Имя ветки**. Несколько ключей
  в имени связывают одну ветку с несколькими задачами; регистр ключа нормализуется.
  Исчезнувшие ветки сохраняются в свёрнутой истории. При повторном создании
  того же имени сохраняется прежняя связь и её tombstone.
  История общей основной ветки не наследуется от новой ветки: коммиты и CI
  появляются через MR или прямую связь. Fork MR требует явного `plane:` маркера.
- Jobs закрепляются по точному ID запуска; retry создаёт отдельный объект.
  Закрепление сохраняет SHA и pipeline. Старый job остаётся закреплённым.
- Все pipelines для SHA собираются с пагинацией. Pipeline с синтетическим
  merge SHA отображается непосредственно под MR, если SHA не соответствует
  доступному коммиту MR. Pipelines реальных MR-коммитов показаны под коммитами.
  Child pipelines запрашиваются отдельно с `source=parent_pipeline`, поскольку
  [GitLab исключает их из обычного списка](https://docs.gitlab.com/api/pipelines/#list-project-pipelines).
- В пилоте MR автоматически наследует CI своего project ID. Pipeline из другого
  source project у fork MR пропускается: его URL можно добавить отдельно после
  подключения исходного репозитория. Автоматическая связь CI между fork и target
  требует отдельной обработки прав и блокировок нескольких репозиториев.
- История и повторённые jobs сворачиваются; текущие jobs остаются видимыми.
  CI summary отдельно считает success, failed, running и waiting;
  `allow_failure` обозначается у job.
- Удаление связи создаёт tombstone, чтобы webhook не восстановил её.
  Повторное добавление URL восстанавливает связь. Объекты и истории не удаляются.
- Неизвестные маркеры записываются в `GitLabDiagnostic`; задачи не создаются.
  Если задача появится позже, reconciliation повторно сопоставит маркеры
  сохранённых коммитов, даже при неизменившихся ветках и отсутствии CI.

## Надёжность и хранение

Webhook проверяет secret в постоянном времени, тип события и allowlist project ID.
Повторные payloads дедуплицируются. В durable outbox сохраняются только ID:
описания, variables, сообщения коммитов и traces из webhook не копируются.
Push/Tag события сохраняют проверенные `before`/`after` SHA. Обработчик сначала
проверяет полный диапазон push, чтобы изменение текущих refs не потеряло
отложенный коммит. Нулевой `after` не запрашивается как коммит.
Обработчик получает актуальные данные через API, поэтому отложенные события
не перезаписывают состояние старым payload. Более старые `updated_at` игнорируются.

Beat восстанавливает pending/failed события каждую минуту и запрашивает
reconciliation каждые 5 минут. Отдельный cursor обнаружения коммитов не изменяется
при событии job/pipeline. Первый проход просматривает историю репозитория;
следующие проверяют SHA веток и тегов и запрашивают пагинируемые диапазоны
`OLD_SHA..NEW_SHA`. Дата коммита не влияет на обнаружение новых push; обе ветви
merge входят в диапазон. Неизменившиеся refs не сканируются повторно; потерянный
старый SHA вызывает полный проход только изменившегося ref. Перекрытие 5 минут
остаётся для обнаружения обновлённых MR. Известные MR, SHA и pipelines проверяются
повторно. Переполнение лимита пагинации сообщает ошибку, не обрезает результат
молча и не продвигает checkpoint. Синхронизация сериализована блокировкой репозитория.
Один проход синхронизации переиспользует своё HTTPS-соединение; Session закрывается
при успехе и ошибке. Соединение не разделяется с личными проверками прав.
Тайм-аут установления соединения — 15 секунд, чтения — 20 секунд;
проверка TLS сертификата включена, HTTP redirects запрещены.

При отказе технического токена сохранённые snapshots остаются в БД. Пользователь
увидит их только после успешной проверки своих прав; UI показывает состояние
подключения и время последней синхронизации. Traces, artifact files, variables
и runner credentials не сохраняются. Секреты шифруются существующим механизмом
Plane (Fernet от SECRET_KEY); смена SECRET_KEY требует переноса credentials.

Перед production: провести реальную доставку webhook на доступный HTTPS API,
проверить OAuth callback и cookie origin, CI visibility и revoked-user сценарий
на рабочих ролях; измерить время reconciliation на выбранных репозиториях.
Репозитории, токены и тестовые данные пилота сохраняются. Production deployment
в рамках локального пилота не выполняется.

При откате на образы до появления GitLab интеграции отключите периодические
задачи `gitlab-event-recovery` и `gitlab-reconciliation` в `PeriodicTask`
(`enabled=False`) и перезапустите beat. DatabaseScheduler сохраняет их в БД;
старый worker не умеет обрабатывать эти задачи. Удалять записи не требуется.
